## Prima cosa da risolvere: regole Codex (HIGH)

Le regole globali Codex con decision=allow possono autorizzare l’esecuzione fuori
dal sandbox. L’adapter tenta di trasformarle in divieti per il worker senza
cambiare la configurazione dell’utente. `codex_rules()` interpreta solo chiamate
letterali e rifiuta policy dinamiche; 65 regole sono state generate sul sistema.

**Il test live finale NON ha confermato l’applicazione dei divieti.**
Un divieto sintetico per `printf AOS_SHADOW_PROBE` non ha impedito l’esecuzione
(exit 0 e stringa realmente stampata). Il file di regole esterno, collegato nella
cartella .codex del task, è invece risultato illeggibile dagli strumenti del
worker (`PRIVATE_RULES_READ_DENIED`). La protezione del contenuto funziona; il
caricamento/applicazione della policy tramite questo collegamento non è provato.
Non confondere exit 0 del processo con PASS del controllo di sicurezza.

Diagnosi successiva: verificare con la CLI installata come caricare un layer
restrittivo senza ereditare autorizzazioni che saltano il sandbox, senza esporre
argomenti privati delle regole al modello, e senza modificare permessi globali.
Nessun aggiramento del sandbox o ampliamento di privilegi. Se non possibile,
dichiarare il runtime incompatibile e bloccarlo. Prima dei benchmark rifare
prove negative reali di regole, letture esterne/segreti, scrittura .git e rete.
La prova precedente con file di regole normale bloccava git push; quella con
symlink introdotta per nascondere dati privati richiede questa nuova diagnosi.
